### 2026-09-15 実在しない staff 行が顧客のスタッフ選択に表示されていた

nun Fukushima の**店舗共用端末**が、staff 行「**nun**」（`role=manager`）で
店長画面にログインして運用されていた。
この行は `archived_at` が null のため、**顧客のスタッフ選択画面（`/review`）にも表示される**。

**実害**: 2026-07-15 の**テスト感想1件のみ**。顧客からの申告はない。

**構造**（調査で確認した事実）:
- 顧客向け `GET /api/staff` の絞り込みは `salon_id` 一致 ＋ `archived_at is null` **のみ**。
  `role` も `line_user_id` も `publish_consent_confirmed_at` も見ていない
  （`src/app/api/staff/route.ts:29-31`）。
- **特定の staff を顧客に非表示にする手段は `archived_at` だけ。**
  `staff` に公開/非公開フラグ列は**存在しない**（全19列を確認）。
- `archived_at` を立てると**同じ行での店長ログインも失効する**
  （`src/lib/staff-session.ts:42` が `archived_at is null` を要求）。
- 物理削除は**できない**。感想が1件ある時点で 409 で拒否される
  （`src/app/api/manager/staff/delete/route.ts:58`）。
- `/kiosk` は **device cookie のみ**で動き **staff 行を必要としない**
  （`src/lib/visit-context.ts:31-33`）。来店受付・特典消し込み・取消・移行の
  5アクションすべてが端末経路で通る。
  一方 `/manager/*` と `/dashboard` の**10画面はすべて manager 必須**で、
  `/kiosk` では代替できない。

**対処**: **共用端末で店長画面を使っているかをスタッフに確認中。**
受付のみなら **`/kiosk` 登録に切り替えてから「nun」行をアーカイブ**する（コード変更なし）。
順序を誤ると店長画面に入れなくなるため、切り替えを先に行う。

**残課題**:
- スタッフからの回答待ち（2026-09-15 時点）
- **他サロンに同じ構造があるかは未確認。**
  「実在の人物でない」を示す列が無いため、SQL では候補抽出までしかできない
  （staff 名がサロン名と一致する行・未受諾の manager 行など）

### 2026-09-06 LINE公式アカウントに未認証の警告が表示されていた

**症状**: 顧客のトーク画面上部に
「このアカウントは未認証アカウントです。投資など金銭に関連する
メッセージには十分注意してください／通報する」
という警告が常時表示されていた。サロンの信用に関わる。

**原因**: LINE公式アカウントを未認証のまま運用していたため。
未認証は誰でも作成でき審査不要だが、灰色バッジと上記の警告が付く。
認証済にすると警告が消え、LINEアプリ内の検索対象になる。
申請は無料、料金プランは変わらない。

**対処**: 2026-09-06、認証済アカウントを申請した。

申請内容:
- 業種: ウェブサービス / ウェブサービス(ビジネス)
- 申し込みタイプ: Webサービス・アプリ
  （echo Labs はSaaS提供者であり店舗運営者ではないため）
- サイト/アプリ名: echo
- URL: https://echo-thanks.jp
- 会社/事業者URL: https://echo-thanks.jp/company
- 連絡先メール: info@echo-thanks.jp
  （運営サイトと同じドメインである必要があるため、
  当初入力されていた個人のgmailから変更した）

審査は5〜10営業日。結果は info@echo-thanks.jp に届く。
途中経過は案内されない。審査中も通常どおり利用できる。
審査に通らなくても未認証のまま継続でき、機能は全て使える。

本人確認のため、申請時の電話番号またはメールに連絡が来る場合がある。
電話の場合は通話が録音される。

**結果（2026-09-11）**: **非承認**。
理由は「審査基準に抵触」とのみ通知され、**具体的な項目は非開示**。
**当面は再申請しない。** Messaging API による通知は**未認証のまま使用**する
（未認証でも機能はすべて使え、審査に通らなくても継続できる）。
**外部サロンへ展開する前に再検討**する。

**残課題**:
- 再申請の要否を外部サロン展開前に判断する（2026-09-11 非承認）
- コーポレートサイトのトップに「2026年12月 提供開始予定」と
  表記されているが、実際は9月時点で5店舗が稼働中。
  正式リリースが12月ならその旨が伝わる表記に直したほうが、
  事業実態と一致する

### 2026-09-03 LINE通知が届かないという申告

**症状**: パイロット3日目、新規登録した顧客から
「LINEが届いていない」という申告が複数。うち1名は Android 端末で、
友だち追加は済んでいた。

**原因**: 一部は仕様どおり。echo が顧客に送る LINE は
「来店後の感想リマインド」1種類のみで（src/lib/line-messaging.ts:123）、
登録した瞬間には何も送られない。送信は来店時刻 +
salons.notify_after_minutes 後、次の cron（10分毎）のとき。
CARTA はこの値が120分だったため、登録直後の確認では届いていない。

Android であることとの因果は確認できていない。push は
サーバー側から送るもので端末OSで挙動が変わる仕組みではない。

**対処**: 申告を受けた時点では仕様の説明のみ。設定値の変更は未実施。

2026-09-03、5店舗すべての salons.notify_after_minutes を 10 に統一した。
統一前は CARTA 120 / Niii 180 / nun 180 / SELNI 60 / suco 10 とばらついており、
パイロットの感想率を店舗間で比較できない状態だった。
テストサロン・デモサロンは 180 のまま。

**残課題**:
- 2時間以上経過後も届いていないケースがあるかは未確認
- skip_reason='not_friend' は9/1以降で18行・実人数9人。
  8/25の修正（1d29da3）より前の残骸ではなく、パイロット期間中の新規発生。
  customers.created_at で内訳を見ると新規顧客3行・既存顧客15行で、
  既存顧客が83%を占める。
  原因は bot_prompt=aggressive が初回ログイン時にしか適用されない構造。
  既にログイン済みの顧客が別店舗の /onboard を開いても認可URLを通らず、
  友だち追加を促す画面が出ない（api/auth/line/login/route.ts:59-63）。
  2026-09-03、notify_after_minutes を10分に統一した効果と合わせて
  1週間観察してから対応を判断する。
- skip_reason='not_friend' は恒久的に閉じるため、cron の判定後に
  友だち追加した顧客にはその回の通知が二度と送られない。
  運用（登録時に友だち追加を確実に行う）で回避するか、
  再送の仕組みを持つかは未判断
- 10分は施術中に通知が届く可能性がある。来店記録は店頭QRまたは
  スタッフのQR読み取りの瞬間に立つため、施術前に読むと施術中に鳴る。
  店頭カード（施術中に顧客がQRを読む運用）と組み合わせると顕在化しうる。
  スタッフから申告があれば調整する。

### 2026-09-02 /mypage の特典に✓が常時表示され、誤解を生んだ

**症状**: 来店1回の新規顧客のマイページで「もらえる特典」に
✓が付いており、「もう特典をもらえる」と誤解された。

**原因**: ✓ は globals.css の .perk-item::before に固定で入っており、
達成判定が存在しなかった。required_count は取得されていたが
描画で参照されていなかった。

**対処**: 未達成（進捗 < required_count）の行に is-locked を付け、
✓を visibility:hidden にしてチップを中立色に落とした。
commit 8404bb8。/review/complete が同じクラスを共用しているため、
変更前後で HTML 全文一致（106,203 bytes、差分は nonce のみ）を確認済み。

**残課題**: なし

### 2026-09-02 スタッフの店舗異動ができなかった

**症状**: Niii で登録済みのスタッフが CARTA の招待リンクを開くと
「既に登録済み」で弾かれ、Niii のマイページに戻される。
複数店舗を持つサロンではアシスタントの異動が毎月起こりうる。

**原因**: 1 LINE = 1 staff 行の構造で、移動する手段が存在しなかった。
resolveStaffByLineUserId() は line_user_id で1行を引く（staff-session.ts:38-45）。

**対処**: /admin/staff を新設し、staff.salon_id を UPDATE する方式で
移動できるようにした。role は移動時に staff にリセット、job_title は引き継ぐ。
そのサロンで唯一の manager は移動・降格を拒否（last_manager）。
作成後に role を変更する経路が存在しなかったため、権限変更フォームも同時に追加。
commit c5ee80c。

**残課題**: 全サロンが対象になっているため、第三者サロンを迎える前に
organizations 概念の導入が必要（40_decisions.md 参照）。

### 2026-09-02 staff.line_user_id に UNIQUE 制約が無かった

**症状**: コードのコメントは「staff.line_user_id は unique」と書かれていたが
（salon/new/route.ts:151）、本番DBに該当する制約が存在しなかった。

**原因**: 未確認。migration に記述があっても本番に適用されていなかった可能性。

**対処**: 部分UNIQUEインデックスを追加。
staff_line_user_id_active_uniq on staff (line_user_id)
where line_user_id is not null and archived_at is null
重複行は当時0件。あわせて resolveStaffByLineUserId() と
staff-invite.ts の Supabase error 握り潰しをログ出力に変更（commit 2285b0f）。
複数行ヒット時に maybeSingle が静かに null を返し、該当者が
エラーもなく全画面から締め出される状態だった。

**残課題**: staff-invite.ts:119-123 の line_taken ガードが archived_at で
絞っていないため、「退職済み1行＋在籍1行」で同じ line_user_id を持つ状態だと
ガードが素通りする。ログには残るようになったが、素通り自体は未修正。
認可の対照確認が必要なため、organizations の導入時に合わせて扱う。
