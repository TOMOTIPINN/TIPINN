### 2026-10-01 /admin/invites の「送信済」チェックが一度も保存できていなかった（解決済み）

**症状**: `/admin/invites`（サロン招待）の「送信済」チェックを入れると画面は `/admin/invites` に戻るが、
チェックは外れたまま。**`salon_invites.sent_at` は NULL のまま**だった。
**2026-08-25（`fc71b88`）の作成時から 2026-10-01 まで、一度も保存できていなかった。**

**影響**: お客様・お金への影響なし（運営者が「送った」と手で付けるメモ欄）。

**原因**: `SentToggle` は hidden の `sent=0` と、チェック時は checkbox の `sent=1` を**同名で両方**送る。
サーバー（`/api/admin/invites/sent`）は `form.get("sent")` で読んでおり、`FormData.get` は
**最初の値（常に "0"）**を返すため、毎回 `sent_at = null` で上書きしていた
（コードのコメントは「同名の後者が採用される」と、仕様と逆に書いていた）。
**UPDATE 自体は成功するので、エラーも画面表示も出ず、誰も気づかなかった。**
5d で同じ部品を使ったオーナー招待（`/api/admin/owner-invites/sent`）も同じ状態だった。

**気づいた経緯**: §21 5d の本番確認で、`SentToggle` に送り先の引数を足した変更の退行確認（対照群）として
サロン招待の送信済みを操作したとき、DB の `sent_at` が NULL のままだと分かった。

**対処**: `form.getAll("sent")` に `"1"` が含まれるかで判定するよう変更（両 API）。送る内容は変えていない。
commit `5961fa0`。2026-10-01 に本番で、サロン招待（ZVGG-0441-R45K）・オーナー招待とも
チェックで保存され、外すと消えることを確認済み（`40_decisions.md` §21「5d の実装と本番確認」）。

**教訓**: **「エラーにならない」は「動いている」ではない。保存系の操作は、画面だけでなく DB の値まで1回は確かめる。**

**残課題**: 送信済みの API が更新した行数を見ておらず、存在しない ID でも成功扱いになる
（`50_security.md` §5-7・未着手）。

### 2026-09-22 スタッフ詳細画面の「累計 0」が不自然に見えた（仕様どおり・ラベルの食い違い・解決済み）

**観測**（2026-09-22・CARTA・歩夢の staff アカウント。`40_decisions.md` §19 確認11 の画面）:
歩夢の詳細画面（`b64be72e`）の下部に **「累計 0」** と表示された。
2026-09-20 の藤原和音（Niii）の詳細では **「累計 5」「累計 7」** だった。
歩夢は `b64be72e` で購入（`f1b2d015`）を受けているため、0 は不自然に見えた。

**原因**（2026-09-22 調査）: **ラベルは「累計」だが、表示している値は `weekCount`**。
- `countEvals(staffId, sinceISO?)`（`src/app/staff/received/[reviewId]/page.tsx:61-76`）は
  そのスタッフ宛ての **`reviews`（感想）＋ `rating_purchases`（評価スタンプ）の件数**を返す
  （¥は数えない。`rating_purchases` は `PAID_STAMPS_ENABLED`＝`true` のときだけ加算）。
- 詳細画面は `weekCount = countEvals(staffId, jstPeriodStartISO("week"))`（**JST の月曜 0:00 以降**）と
  `totalCount = countEvals(staffId)`（通算）の2つを取る（`:206-212`）が、
  **フッターの「累計」に出しているのは `weekCount`**（`:303-306`）。
  `totalCount` はランク用で、ランクは `RANK_ENABLED` が偽のため**通算の数字はどこにも出ていない**。
- 歩夢の `b64be72e` は **9/17 の分で今週（9/21 月曜〜）に入らない**ため 0 だった。
  藤原和音の 9/20（日）は §19 の確認で感想・購入を作った週（9/14〜）の件数。

**判定**: **データは正しい。ラベルと中身の食い違い**（不具合ではない）。

**対処（2026-09-22 決定）**: **ラベルを「今週」に直す。値（`weekCount`）は変えない。**
- **通算（`totalCount`）を出す案は採らない。** 通算の数字はスタッフ同士の比較につながり、
  `40_decisions.md` §18 A「スタッフをスコア化しない」とぶつかるため。

**他画面**: `src` 全体で「累計」の表示文言を確認した（2026-09-22）。来店回数の「累計 N 回」
（`/visit`・`/staff/visit`・`/mypage`）と `/dashboard` の「VIP顧客数（累計）」は、いずれも
**通算・期間非連動の値**でラベルと一致しており、同じ食い違いは無い。

**実装**: `f329d52`（ラベルを「今週」に変更・値と計算は不変）。

**本番実機確認**（2026-09-22 10:30・CARTA・原（運営者本人）の staff アカウント）:
詳細画面の下部が **「今週 0」** になっていることを確認した（`f329d52` のラベル変更が本番に反映）。

**残課題**: ~~ラベル変更の本番実機確認~~ → **解消（2026-09-22）**。**この項目は解決済み。**

### 2026-09-02 staff.line_user_id に UNIQUE 制約が無かった

**症状**: コードのコメントは「staff.line_user_id は unique」と書かれていたが
（salon/new/route.ts:151）、本番DBに該当する制約が存在しなかった。

**原因**: 未確認。migration に記述があっても本番に適用されていなかった可能性。

**対処**: 部分UNIQUEインデックスを追加。
staff_line_user_id_active_uniq on staff (line_user_id)
where line_user_id is not null and archived_at is null
重複行は当時0件。あわせて resolveStaffByLineUserId() と
staff-invite.ts の Supabase error 握り潰しをログ出力に変更（commit 2285b0f）。
複数行ヒット時に maybeSingle が静かに null を返し、該当者が
エラーもなく全画面から締め出される状態だった。

**残課題**: staff-invite.ts:119-123 の line_taken ガードが archived_at で
絞っていないため、「退職済み1行＋在籍1行」で同じ line_user_id を持つ状態だと
ガードが素通りする。ログには残るようになったが、素通り自体は未修正。
認可の対照確認が必要なため、organizations の導入時に合わせて扱う。

**★訂正（2026-09-23）★** — §21 の調査で `pg_indexes` から本番の実定義を直接取得した結果、
上の記録は現状と食い違っている。**以下が本番の事実。**

本番の `staff` には **2本とも存在する**:

```
uq_staff_line_user_id
  CREATE UNIQUE INDEX uq_staff_line_user_id ON public.staff USING btree (line_user_id)
  WHERE (line_user_id IS NOT NULL)

staff_line_user_id_active_uniq
  CREATE UNIQUE INDEX staff_line_user_id_active_uniq ON public.staff USING btree (line_user_id)
  WHERE ((line_user_id IS NOT NULL) AND (archived_at IS NULL))
```

- 前者は **archived 条件を持たない**ため後者を包含する。実効的な制約は
  **「1 LINE = staff 行は退職者を含めて最大1行」**。後者は冗長。
- **9/2 の「本番DBに該当する制約が存在しなかった」という記録は、現状と食い違う。**
  **食い違いの原因は未確認**（9/2 時点で本当に無かったのか、別名で探して見落としたのかは分からない）。
- **上の「残課題」は成立しない。** 「退職済み1行＋在籍1行」は
  `uq_staff_line_user_id` があるため **DB で作れない**。line_taken ガードの素通りは
  起こり得ない状態になっている（コードは未修正のままでよい）。

**代わりに残る課題**: **アーカイブした staff は `line_user_id` を占有し続ける。**
`archived_at` を入れても LINE は解放されない（`api/manager/staff/archive` は
「`line_user_id` / `invite_token` も触らない＝復帰時にそのまま戻す」）。
そのため**退職者は別サロンに新しい staff 行として入れない**
（`/api/staff/bind` も `/api/manager/salon/new` も unique 違反で落ちる）。
解放されるのは `/api/manager/staff/delete` の **hard delete（行ごと削除）だけ**。
移動は `/admin/staff/transfer`（行の `salon_id` を UPDATE）でのみ可能。
→ **§21 とは別の未着手課題（扱う時期は未定）。** §21 の実装順には含めない。

**教訓**: **migration だけでなく docs の記録も本番の真実ではない。**
実定義は `pg_indexes` / `pg_constraint` など **`pg_*` から確認する**
（`40_decisions.md` §1.11「記録が正しいかの唯一の実効テストは『migrations だけで作り直せるか』」の系）。
